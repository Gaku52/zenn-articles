4. **docker run / stop / rm** の基本操作を実践できるようになる

## Docker のアーキテクチャ

Docker はクライアント・サーバー型のアーキテクチャで動作しています。大きく分けて 3 つのコンポーネントから構成されます。

### Docker デーモン（dockerd）

Docker デーモンは、コンテナの作成・実行・管理を担当するバックグラウンドプロセスです。ホストマシン上で常時稼働しており、Docker API のリクエストを受け付けて処理します。

- イメージのビルドと管理
- コンテナの起動・停止・削除
- ネットワークやボリュームの管理

Docker Desktop をインストールすると、このデーモンが自動的に起動します。

### Docker クライアント（docker CLI）

私たちが普段ターミナルで入力する `docker` コマンドが、Docker クライアントです。クライアントはユーザーの操作を Docker API のリクエストに変換し、デーモンに送信します。

```bash
# このコマンドを実行すると...
docker run hello-world

# 1. クライアントがデーモンに「hello-world イメージでコンテナを起動して」とリクエスト
# 2. デーモンがイメージを探し、なければレジストリから取得
# 3. デーモンがコンテナを作成・起動
# 4. 実行結果がクライアント経由でターミナルに表示される
```

### Docker レジストリ（Docker Hub 等）

レジストリは、Docker イメージを保存・配布するためのサービスです。代表的なものに **Docker Hub** があります。公式イメージ（nginx、postgres、node など）はすべて Docker Hub で公開されています。

```bash
# Docker Hub から nginx イメージを取得する
docker pull nginx:alpine

# 自分で作ったイメージを Docker Hub にアップロードする
docker push myuser/myapp:v1.0
```

企業では AWS ECR や GitHub Container Registry などのプライベートレジストリも利用されています。

### 3 つのコンポーネントの関係

```
  Docker クライアント          Docker デーモン
  (docker CLI)        API     (dockerd)
  docker run ...   -------->  コンテナ・イメージ管理
  docker build ..              ネットワーク・ボリューム管理
  docker pull ...                    |
                                     | pull / push
                                     v
                            Docker レジストリ
                            (Docker Hub 等)
                            nginx, postgres, node ...
```

クライアントとデーモンは同じマシン上で動くのが一般的ですが、リモートのデーモンに接続することも可能です。

## イメージとコンテナの関係

Docker を理解するうえで最も重要な概念が、**イメージ**と**コンテナ**の違いです。

### イメージとは

イメージは、アプリケーションの実行に必要なファイルシステムと設定をまとめた**読み取り専用のテンプレート**です。複数のレイヤーが積み重なった構造になっています。

```
┌──────────────────────────────┐
│  イメージ（読み取り専用）        │
│                              │
│  Layer 3: アプリケーションコード │
│  Layer 2: 依存パッケージ        │
│  Layer 1: ベース OS (alpine 等) │
└──────────────────────────────┘
```

プログラミングに例えると、イメージは「クラス定義」に相当します。それ自体は動きませんが、設計図としての役割を果たします。

### コンテナとは

コンテナは、イメージから作成された**実行中のインスタンス**です。イメージの上に書き込み可能なレイヤーが追加され、プロセスとして動作します。

```
┌──────────────────────────────┐
│  コンテナ（実行中インスタンス）   │
│                              │
│  書き込み可能レイヤー（コンテナ固有）│
│  ─────────────────────────── │
│  イメージレイヤー（読み取り専用）  │
└──────────────────────────────┘
```

1 つのイメージから複数のコンテナを作成できます。これはクラスから複数のインスタンスを生成するのと同じ考え方です。

```bash
# 同じ nginx イメージから 3 つのコンテナを起動する
docker run -d --name web1 -p 8081:80 nginx:alpine
docker run -d --name web2 -p 8082:80 nginx:alpine
docker run -d --name web3 -p 8083:80 nginx:alpine
```

### 仮想マシンとの違い

Docker コンテナは仮想マシン（VM）とよく比較されます。両者の違いを理解しておくことが大切です。

| 比較項目 | 仮想マシン（VM） | コンテナ |
|---|---|---|
| 起動時間 | 数分 | 数秒 |
| サイズ | 数 GB | 数十 MB |
| OS | ゲスト OS が必要 | ホスト OS のカーネルを共有 |
| オーバーヘッド | 大きい | 小さい |
| 分離レベル | 高い（ハードウェアレベル） | 中程度（プロセスレベル） |

コンテナはホスト OS のカーネルを共有するため、VM と比べて圧倒的に軽量で高速です。その代わり、分離レベルは VM よりやや低くなります。

## コンテナのライフサイクル

コンテナには明確な状態遷移（ライフサイクル）があります。これを理解しておくと、トラブル時の原因特定に役立ちます。

### 状態遷移の全体像

```
               docker create
                    |
                    v
 +--------+   +---------+   docker start    +---------+
 | (なし)  |-->| Created |----------------->| Running |
 +--------+   +---------+                   +---------+
                    |                         |   |   |
                    | docker rm               |   |   |
                    v                         |   |   |
               (削除される)                    |   |   |
                                              |   |   |
                    docker stop               |   |   |
                    +-------------------------+   |   |
                    v                             |   |
               +---------+    docker restart      |   |
               | Exited  |--------------------->--+   |
               +---------+                           |
                    |          docker pause           |
                    | docker rm     |                 |
                    v               v                 |
               (削除される)    +----------+            |
                              |  Paused  |------>-----+
                              +----------+ docker unpause
```

### 各状態の説明

| 状態 | 説明 | 代表的な遷移コマンド |
|---|---|---|
| Created | コンテナが作成されたが、まだ起動していません | `docker create` |
| Running | コンテナのプロセスが実行中です | `docker start` / `docker run` |
| Paused | コンテナのプロセスが一時停止しています | `docker pause` |
| Exited | メインプロセスが終了し、コンテナが停止しています | `docker stop` / プロセス終了 |
| Dead | 異常終了した状態です（リソース解放に失敗した場合など） | 異常発生時 |

覚えておくべきポイントは、**コンテナはメインプロセス（PID 1）が終了すると自動的に停止する**ということです。`echo "hello"` のように一瞬で終わるコマンドを実行すると、コンテナもすぐに Exited 状態になります。

## docker run：コンテナを起動する

`docker run` は最もよく使うコマンドです。イメージからコンテナを作成し、起動するまでを一度に行います。

### 基本構文

```bash
docker run [オプション] イメージ名[:タグ] [コマンド] [引数...]
```

### シンプルな実行

```bash
# alpine イメージで echo コマンドを実行する
docker run --rm alpine echo "Hello, Docker!"
# Hello, Docker!
```

`--rm` オプションを付けると、コンテナ終了時に自動的に削除されます。テストや一時的な実行では必ず付けるようにしましょう。付けないと停止済みのコンテナがどんどん溜まっていきます。

### インタラクティブモード（-it）

コンテナの中に入ってシェル操作をしたい場合は、`-it` オプションを使います。

```bash
# コンテナ内でシェルを起動する
docker run -it --rm alpine /bin/sh

/ # ls
/ # cat /etc/os-release
/ # exit   # コンテナから抜ける（コンテナも終了する）
```

- `-i`（interactive）：標準入力を開いたままにします
- `-t`（tty）：疑似ターミナルを割り当てます

この 2 つを組み合わせることで、対話的な操作が可能になります。

### バックグラウンド実行（-d）

Web サーバーのように常時稼働させたいコンテナは、`-d`（detach）オプションでバックグラウンド実行します。

```bash
# nginx をバックグラウンドで起動する
docker run -d --name my-nginx -p 8080:80 nginx:alpine

# 動作確認
curl http://localhost:8080
```

ここで使っているオプションを整理します。

| オプション | 意味 |
|---|---|
| `-d` | バックグラウンドで実行します |
| `--name my-nginx` | コンテナに `my-nginx` という名前を付けます |
| `-p 8080:80` | ホストの 8080 番ポートをコンテナの 80 番ポートに接続します |

ポートマッピング `-p` の書式は **ホスト:コンテナ** の順番です。「外側（ホスト）から内側（コンテナ）へ」と覚えておくとよいでしょう。

### 環境変数の設定（-e）

コンテナに環境変数を渡すには `-e` オプションを使います。

```bash
# PostgreSQL を環境変数付きで起動する
docker run -d --name my-db \
    -e POSTGRES_USER=admin \
    -e POSTGRES_PASSWORD=secret123 \
    -e POSTGRES_DB=myapp \
    -p 5432:5432 \
    postgres:16-alpine
```

環境変数が多い場合は、`.env` ファイルにまとめて `--env-file` で読み込むこともできます。

```bash
docker run -d --name my-db \
    --env-file .env \
    -p 5432:5432 \
    postgres:16-alpine
```

## docker stop：コンテナを停止する

実行中のコンテナを停止するには `docker stop` を使います。`docker stop` は以下の手順でコンテナを安全に終了させます。

1. コンテナのメインプロセスに **SIGTERM** シグナルを送信します
2. プロセスがグレースフルシャットダウンするのを待ちます（デフォルト 10 秒）
3. 10 秒経っても終了しない場合、**SIGKILL** で強制終了します

```bash
# タイムアウトを変更する場合
docker stop -t 30 my-nginx

# すぐに強制終了させたい場合
docker kill my-nginx

# 複数コンテナの一括停止
docker stop my-nginx my-db my-redis
```

---

## docker rm：コンテナを削除する

停止したコンテナを削除するには `docker rm` を使います。

```bash
# 停止済みのコンテナを削除する
docker rm my-nginx

# 停止 + 削除を一度に行う（-f オプション）
docker rm -f my-nginx

# 停止中の全コンテナを一括削除する
docker container prune
```

### コンテナの一覧を確認する

現在のコンテナの状態を確認するには `docker ps` を使います。

```bash
# 実行中のコンテナを一覧表示する
docker ps

# 停止中のコンテナも含めてすべて表示する
docker ps -a

# 表示例:
# CONTAINER ID   IMAGE          STATUS         PORTS                  NAMES
# a1b2c3d4e5f6   nginx:alpine   Up 5 minutes   0.0.0.0:8080->80/tcp   my-nginx
# f6e5d4c3b2a1   postgres:16    Exited (0)                            my-db
```

## 基本操作の流れを実践してみよう

ここまでの知識を使って、一連の操作を通しで試してみましょう。

```bash
# 1. nginx コンテナをバックグラウンドで起動する
docker run -d --name practice-web -p 8080:80 nginx:alpine

# 2. 動作確認する
docker ps
curl http://localhost:8080

# 3. ログを確認する
docker logs practice-web

# 4. 停止 → 確認 → 削除 → 確認
docker stop practice-web
docker ps -a          # Exited 状態で表示される
docker rm practice-web
docker ps -a          # 表示されなくなる
```

この一連の流れ（起動 → 確認 → 停止 → 削除）が Docker 操作の基本サイクルです。

## やってみよう！

以下の演習に取り組んで、この章の理解を深めましょう。

### 演習 1：コンテナの基本操作

`alpine` イメージを使って、以下の操作を順番に行ってください。

1. `docker run --rm alpine cat /etc/os-release` を実行し、OS 情報を確認する
2. `docker run -it --rm alpine /bin/sh` でコンテナに入り、`ls /` や `whoami` を実行してみる
3. `exit` でコンテナから抜け、`docker ps -a` で残っているコンテナがないことを確認する

### 演習 2：Web サーバーの起動と停止

nginx を使ったコンテナのライフサイクルを体験してください。

1. `docker run -d --name ex-web -p 9090:80 nginx:alpine` で nginx を起動する
2. `curl http://localhost:9090` でアクセスできることを確認する
3. `docker logs ex-web` でアクセスログを確認する
4. `docker stop ex-web` で停止し、`docker ps -a` で Exited 状態を確認する
5. `docker start ex-web` で再起動し、再び `curl` でアクセスできることを確認する
6. `docker rm -f ex-web` で停止と削除を同時に行う

### 演習 3：環境変数を使ったコンテナ起動

環境変数を渡してコンテナ内で参照してみましょう。

1. `docker run --rm -e MY_NAME=Docker alpine echo "Hello, $MY_NAME"` を実行する
2. 期待した出力にならない場合、`docker run --rm -e MY_NAME=Docker alpine sh -c 'echo "Hello, $MY_NAME"'` を試す
3. なぜ結果が異なるのか考えてみましょう（ヒント：変数展開がどこで行われるかがポイントです）
