## はじめに

Web アプリケーションを開発するうえで、「認証（Authentication）」は避けて通れないテーマです。ログイン画面を作るだけでは不十分で、**なぜその仕組みが必要なのか**、**どのような方式があるのか**を体系的に理解しておくことが、安全なシステムを構築するための第一歩となります。

この章では、認証の根幹となる **3 つの認証要素**、リクエスト処理における**認証フローの全体像**、**HTTP 認証の仕組み**、そして**ステートレス認証とステートフル認証の違い**を丁寧に解説します。

---

## 認証とは何か

認証（Authentication、略称 AuthN）とは、「**あなたは誰ですか？**」という問いに答えるプロセスです。システムにアクセスしようとしているユーザーが、本当に本人であるかどうかを確認します。

```
認証の基本的な流れ:

  ユーザー:   「私は alice@example.com です」
  システム:   「パスワードで証明してください」
  ユーザー:   「********」
  システム:   「確認しました。alice さんですね」
```

認証と混同されやすい概念に**認可（Authorization、略称 AuthZ）**があります。認可は「**あなたに何が許されていますか？**」を判定するプロセスです。認証と認可は必ず **認証 → 認可** の順序で行われ、認証なしに認可はできません。

| 項目 | 認証（AuthN） | 認可（AuthZ） |
|------|-------------|-------------|
| 質問 | Who are you? | What can you do? |
| タイミング | 最初に実行 | 認証後に実行 |
| 失敗時 | 401 Unauthorized | 403 Forbidden |
| 技術例 | パスワード、JWT | RBAC、ABAC |

## 認証の 3 要素（Authentication Factors）

認証の世界では、ユーザーの身元を証明する手段を **3 つの要素（ファクター）** に分類します。これはセキュリティの基本中の基本であり、多要素認証（MFA）を理解するための土台です。

### 1. 知識要素（Something You Know）

ユーザーが**知っている情報**による認証です。

- パスワード
- PIN コード
- 秘密の質問の回答

最も広く普及していますが、**最も脆弱な要素**でもあります。パスワードの使い回し、フィッシング、ブルートフォース攻撃など、多くの攻撃手法の対象になります。

### 2. 所有要素（Something You Have）

ユーザーが**持っているもの**による認証です。

- スマートフォン（TOTP アプリ、SMS コード）
- ハードウェアセキュリティキー（YubiKey など）
- IC カード

物理的なデバイスの所有を証明する必要があるため、リモートからの攻撃に対して知識要素よりも耐性があります。

### 3. 生体要素（Something You Are）

ユーザーの**身体的特徴**による認証です。

- 指紋認証
- 顔認証（Face ID など）
- 虹彩認証
- 声紋認証

利便性が高い反面、**一度漏洩すると変更できない**という特有のリスクがあります。パスワードは変更できますが、指紋は変えられません。

### 多要素認証（MFA）の考え方

多要素認証とは、**異なる種類の要素を 2 つ以上組み合わせる**認証方式です。同じ種類の要素を 2 つ使っても多要素とは呼びません。

```
正しい多要素認証の例:
  ○ パスワード（知識）+ TOTP コード（所有）  = 2FA
  ○ パスワード（知識）+ 指紋（生体）          = 2FA
  ○ PIN（知識）+ IC カード（所有）+ 顔認証（生体） = 3FA

多要素ではない例:
  × パスワード（知識）+ 秘密の質問（知識）
    → 両方とも「知識要素」なので単一要素認証
```

### 認証方式の強度比較

各認証方式には、それぞれ得意・不得意な攻撃パターンがあります。以下の表で強度と利便性を比較してみましょう。

| 方式 | 強度 | 利便性 | フィッシング耐性 | リモート攻撃耐性 |
|------|------|--------|----------------|----------------|
| パスワードのみ | 低 | 高 | 脆弱 | 脆弱 |
| パスワード + SMS | 中 | 中 | やや脆弱 | SIM swap に脆弱 |
| パスワード + TOTP | 高 | 中 | やや脆弱 | 耐性あり |
| Passkeys（FIDO2） | 高 | 高 | 耐性あり | 耐性あり |
| ハードウェアキー | 最高 | 中 | 耐性あり | 耐性あり |

現在のベストプラクティスとしては、**Passkeys**（パスキー）が強度と利便性の両面で最もバランスが良いとされています。

## 認証フローの全体像

実際のアプリケーションでは、認証は単独で動くのではなく、リクエスト処理パイプラインの一部として機能します。HTTP リクエストがビジネスロジックに到達するまでの流れを見てみましょう。

```
リクエスト処理パイプライン:

  HTTP リクエスト
       │
       ▼
  ┌─────────────────┐
  │ 1. TLS 終端      │  通信の暗号化を確認
  └────────┬────────┘
           │
           ▼
  ┌─────────────────┐
  │ 2. レート制限     │  ブルートフォース防止
  └────────┬────────┘
           │
           ▼
  ┌─────────────────┐
  │ 3. CORS チェック  │  ブラウザセキュリティ
  └────────┬────────┘
           │
           ▼
  ┌─────────────────┐
  │ 4. 認証（AuthN）  │  ← ユーザーの身元確認
  │    → 401 or 続行 │
  └────────┬────────┘
           │
           ▼
  ┌─────────────────┐
  │ 5. 認可（AuthZ）  │  ← 権限の確認
  │    → 403 or 続行 │
  └────────┬────────┘
           │
           ▼
  ┌─────────────────┐
  │ 6. 入力検証      │  XSS / SQLi 防止
  └────────┬────────┘
           │
           ▼
  ┌─────────────────┐
  │ 7. ビジネスロジック│  実際の処理
  └────────┬────────┘
           │
           ▼
  ┌─────────────────┐
  │ 8. 監査ログ      │  誰が何をしたか記録
  └─────────────────┘
```

認証はパイプラインの **ステップ 4** に位置しています。TLS による暗号化やレート制限といった前段の防御を通過したリクエストに対して、ユーザーの身元確認を行います。認証に失敗した場合は **401 Unauthorized** を返し、後続の処理には進みません。

## HTTP 認証の仕組み

HTTP プロトコルには、標準的な認証の仕組みが組み込まれています。ここでは代表的な 3 つの方式を紹介します。

### Basic 認証

最もシンプルな HTTP 認証方式です。ユーザー名とパスワードを Base64 エンコードして `Authorization` ヘッダーに含めます。

```http
GET /api/resource HTTP/1.1
Authorization: Basic YWxpY2U6cGFzc3dvcmQxMjM=
```

`YWxpY2U6cGFzc3dvcmQxMjM=` は `alice:password123` を Base64 エンコードしたものです。

**注意点**: Base64 は暗号化ではなく単なるエンコードです。誰でもデコードできるため、**必ず HTTPS と組み合わせて**使用してください。Basic 認証は開発環境や内部ツールでの利用に留め、本番環境の一般向けサービスでの使用は推奨されません。

### Bearer トークン認証

OAuth 2.0 や JWT でよく使われる方式です。事前に取得したトークンを `Authorization` ヘッダーに含めてリクエストを送ります。

```http
GET /api/resource HTTP/1.1
Authorization: Bearer eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9...
```

Bearer トークンの特徴は以下のとおりです。

- トークン自体に有効期限やユーザー情報を含められます（JWT の場合）
- サーバーはトークンの署名を検証するだけで認証できます
- API やモバイルアプリとの相性が良い方式です

### Digest 認証

Basic 認証の弱点（パスワードが平文で送信される問題）を改善した方式です。パスワードのハッシュ値とサーバーが生成するランダムな値（nonce）を組み合わせて認証を行います。

```
認証フロー:
  1. クライアント → サーバー: リソース要求
  2. サーバー → クライアント: 401 + nonce 値
  3. クライアント: MD5(username:realm:password) + nonce でハッシュ生成
  4. クライアント → サーバー: ハッシュ値を送信
  5. サーバー: 同じ計算をして照合
```

ただし現代のWeb開発では、HTTPS の普及により Digest 認証を使う場面は減っています。Bearer トークン + HTTPS の組み合わせが主流です。

### HTTP 認証方式の使い分け

| 方式 | 用途 | セキュリティ | 現在の推奨度 |
|------|------|------------|------------|
| Basic | 開発環境、内部ツール | 低（HTTPS 必須） | 限定的 |
| Bearer | API、SPA、モバイル | 高 | 推奨 |
| Digest | レガシーシステム | 中 | 非推奨 |

## ステートフル認証 vs ステートレス認証

認証の実装方式は、大きく「ステートフル」と「ステートレス」に分かれます。この違いを理解することは、アーキテクチャ設計の要です。

### ステートフル認証（セッション方式）

サーバー側にユーザーの認証状態（セッション）を保持する方式です。

```
セッション方式の流れ:

  クライアント                サーバー               セッションストア
      │                       │                       │
      │ POST /login           │                       │
      │ {email, password}     │                       │
      │──────────────────────>│                       │
      │                       │ パスワード検証          │
      │                       │ セッション作成          │
      │                       │──────────────────────>│
      │                       │                       │
      │ Set-Cookie:           │                       │
      │ session_id=<sid>;     │                       │
      │ HttpOnly; Secure      │                       │
      │<──────────────────────│                       │
      │                       │                       │
      │ GET /api/data         │                       │
      │ Cookie: session_id=sid│                       │
      │──────────────────────>│                       │
      │                       │ セッション照会          │
      │                       │──────────────────────>│
      │                       │ {userId, roles, ...}  │
      │                       │<──────────────────────│
      │                       │ 認証・認可チェック      │
      │ 200 OK + data         │                       │
      │<──────────────────────│                       │
```

**メリット**:
- サーバー側で即座にセッションを無効化できます（ログアウト、強制切断）
- セッションデータの更新が容易です
- Cookie の `HttpOnly` 属性により XSS からトークン窃取を防げます
- セッションデータのサイズに実質的な制限がありません

**デメリット**:
- サーバーにセッションストア（Redis など）が必要です
- スケーリング時にセッション情報の共有が必要になります
- マイクロサービス間でのセッション共有が困難です

### ステートレス認証（トークン方式 / JWT）

サーバー側に状態を持たず、トークン自体にユーザー情報を含める方式です。

```
JWT 方式の流れ:

  クライアント                サーバー
      │                       │
      │ POST /login           │
      │ {email, password}     │
      │──────────────────────>│
      │                       │ パスワード検証
      │                       │ JWT 生成（署名付き）
      │                       │
      │ {                     │
      │   access_token: "ey.."│
      │   expires_in: 3600    │
      │ }                     │
      │<──────────────────────│
      │                       │
      │ GET /api/data         │
      │ Authorization:        │
      │ Bearer ey..           │
      │──────────────────────>│
      │                       │ JWT 署名検証（公開鍵）
      │                       │ 有効期限チェック
      │                       │ クレームで認可
      │                       │ （DB アクセス不要!）
      │ 200 OK + data         │
      │<──────────────────────│
```

**メリット**:
- サーバーにセッションストアが不要です（ステートレス）
- どのサーバーでもトークンを検証できるため、スケーリングが容易です
- マイクロサービス間では公開鍵を共有するだけで済みます
- モバイルアプリや SPA との統合が容易です

**デメリット**:
- トークンの即時無効化が困難です（ブラックリスト機構が別途必要）
- HTTP ヘッダーのサイズ制限（約 8KB）によりペイロードに制約があります
- トークンが漏洩すると有効期限まで悪用される可能性があります
- 権限変更がトークン再発行まで反映されません

### どちらを選ぶべきか

以下の表を参考に、プロジェクトの特性に合わせて選択してください。

| 判断基準 | セッション方式 | トークン方式（JWT） |
|---------|-------------|-----------------|
| アーキテクチャ | モノリシック | マイクロサービス / SPA |
| ステート管理 | サーバー側 | クライアント側 |
| スケーラビリティ | ストア共有が必要 | 容易（ステートレス） |
| 即時無効化 | 可能 | 困難（ブラックリスト要） |
| DB アクセス | 毎リクエスト | 不要（検証のみ） |
| 適したケース | 伝統的 Web アプリ | API、モバイル、SPA |

:::message
**実務でのヒント**: 最近では **BFF（Backend for Frontend）パターン**として、フロントエンドとの通信にはセッション方式を使い、バックエンドのマイクロサービス間では JWT を使うハイブリッド構成も広く採用されています。
:::

## まとめ

この章で学んだ内容を整理します。

| 概念 | ポイント |
|------|---------|
| 認証とは | 「あなたは誰か？」を確認するプロセス。失敗時は 401 を返す |
| 知識要素 | パスワード、PIN など。最も普及しているが最も脆弱 |
| 所有要素 | スマホ、セキュリティキーなど。リモート攻撃に強い |
| 生体要素 | 指紋、顔認証など。便利だが漏洩時に変更できない |
| 多要素認証（MFA） | 異なる種類の要素を 2 つ以上組み合わせる方式 |
| 認証フロー | TLS → レート制限 → CORS → 認証 → 認可 → ビジネスロジック |
| Basic 認証 | シンプルだが Base64 エンコードのみ。HTTPS 必須 |
| Bearer 認証 | JWT / OAuth で主流。API に最適 |
| ステートフル認証 | セッション方式。即時無効化可能だがストアが必要 |
| ステートレス認証 | JWT 方式。スケーラブルだが即時無効化が困難 |

## やってみよう！

以下の演習で、この章の理解を確かめましょう。

### 演習 1: 認証要素の分類

次の認証手段が「知識・所有・生体」のどれに該当するか分類してください。

1. 銀行の暗証番号（4 桁）
2. SMS で届くワンタイムコード
3. Windows Hello の顔認証
4. 「母親の旧姓は？」という質問
5. YubiKey によるタッチ認証

:::details 回答例
1. **知識要素** -- 本人が記憶している情報です
2. **所有要素** -- スマートフォンを持っていることの証明です
3. **生体要素** -- 顔の特徴による本人確認です
4. **知識要素** -- 本人が知っている情報です（秘密の質問）
5. **所有要素** -- 物理デバイスの所有を証明します
:::

### 演習 2: 多要素認証の判定

以下の組み合わせが「多要素認証」として有効かどうか判定してください。

1. パスワード + PIN コード
2. パスワード + Google Authenticator の 6 桁コード
3. 指紋認証 + 顔認証
4. パスワード + YubiKey + 指紋認証

:::details 回答例
1. **無効** -- 両方とも知識要素のため、単一要素です
2. **有効（2FA）** -- 知識要素 + 所有要素の組み合わせです
3. **無効** -- 両方とも生体要素のため、単一要素です
4. **有効（3FA）** -- 知識 + 所有 + 生体の 3 要素すべてを使用しています
:::

### 演習 3: 認証方式の選定

次のシナリオに最適な認証方式（セッション / JWT）を選び、理由を考えてみてください。

1. Ruby on Rails で作る社内管理ツール（ユーザー数 50 人）
2. React SPA + Go API のマイクロサービス構成（ユーザー数 10 万人）
3. Next.js のフルスタックアプリ（SSR あり）

:::details 回答例
1. **セッション方式** -- モノリシック構成でユーザー数が少なく、即時ログアウトも容易です
2. **JWT 方式** -- SPA + API 構成でスケーラビリティが重要。マイクロサービス間の認証にも適しています
3. **BFF パターン（ハイブリッド）** -- SSR 側でセッションを管理し、API 呼び出しに JWT を使う構成が適しています
:::
