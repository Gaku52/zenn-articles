## この本で学べること

Web アプリケーション開発において、認証と認可はセキュリティの根幹をなす仕組みです。しかし、これらの概念を正確に区別し、適切に実装できるエンジニアは意外なほど多くありません。

本書は、認証認可の基礎から実践的な実装パターンまでを体系的に解説します。パスワードの安全な取り扱いから、セッション管理、JWT、OAuth 2.0、OpenID Connect、そしてロールベースアクセス制御や多要素認証に至るまで、現代の Web 開発で必要となる認証認可の知識をひとつずつ積み上げていきます。

本章では、まず認証と認可の違いを明確にし、なぜこれらを学ぶ必要があるのかを確認します。そのうえで、セキュリティ脅威の全体像と、本書全体の構成をご紹介します。

## 認証と認可の違い

認証と認可は、しばしば混同される概念です。しかし、この 2 つは明確に異なる役割を持っています。

### 認証（Authentication / AuthN）とは

認証とは、「あなたは誰ですか？」という問いに答えるプロセスです。ユーザーの身元を確認する仕組みであり、システムにアクセスしようとしている人物が、本当に主張どおりの本人であるかを検証します。

日常生活に例えると、パスポートや運転免許証を提示して本人確認を行うことに相当します。Web の世界では、パスワードの入力、指紋認証、Google アカウントによるログインなどがこれにあたります。

認証が成功すると、システムはそのユーザーに一意の識別子（ユーザー ID）を割り当て、以降のリクエストでそのユーザーを特定できるようにします。認証に失敗した場合、HTTP では `401 Unauthorized` ステータスコードが返されます。

### 認可（Authorization / AuthZ）とは

認可とは、「あなたに何が許されていますか？」という問いに答えるプロセスです。認証によって身元が確認されたユーザーに対して、どのリソースにアクセスでき、どの操作を実行できるかを判定します。

日常生活では、社員証で入館した後に「この部屋には入れるが、あの部屋には入れない」と区別されることに相当します。Web の世界では、管理画面へのアクセス権限や、ファイルの編集・削除権限の判定がこれにあたります。

認可に失敗した場合、HTTP では `403 Forbidden` ステータスコードが返されます。これは「あなたが誰かはわかっているが、その操作は許可されていない」という意味です。

### 認証と認可の比較

両者の違いを表にまとめると、次のようになります。

| 項目 | 認証（AuthN） | 認可（AuthZ） |
|:---|:---|:---|
| 質問 | Who are you? | What can you do? |
| タイミング | 最初に実行 | 認証の後に実行 |
| 入力 | クレデンシャル（ID/パスワード等） | ユーザー属性・ロール |
| 出力 | ユーザー ID | 許可 / 拒否 |
| 失敗時の HTTP ステータス | 401 Unauthorized | 403 Forbidden |
| 代表的な技術 | パスワード、JWT、OIDC | RBAC、ABAC、ReBAC |
| 変更の主導者 | ユーザー自身 | 管理者 |
| データの保存場所 | DB / IdP | ポリシーエンジン |

とくに重要なのは「認証 → 認可」という順序です。認証なしに認可は成立しません。まず「あなたは誰か」を確認してから、「あなたに何が許されているか」を判定します。ただし、認証されたからといって、すべてが認可されるわけではありません。

### 境界が曖昧になるケース

実務では、認証と認可の境界が明確でないケースも存在します。代表的な例をいくつか挙げます。

**API キー**: API キー自体がクライアントの身元証明（認証）として機能し、同時にキーに紐づくスコープで権限制御（認可）も行います。キーが漏洩すると、認証と認可の両方が突破されるリスクがあります。

**OAuth 2.0 のスコープ**: OAuth は本来「認可の委譲」プロトコルですが、OpenID Connect を加えることで認証も担います。`scope=openid` が認証、`scope=read:user` が認可に対応します。

**JWT のクレーム**: `sub` クレームは認証情報（誰か）を表し、`role` や `permissions` クレームは認可情報（何ができるか）を表します。1 つのトークンに認証と認可の両方が含まれています。

これらのケースを正しく理解し、設計時に認証と認可の責務を分離して考えることが、堅牢なセキュリティアーキテクチャにつながります。

## なぜ認証認可を学ぶのか

「フレームワークが用意してくれるから、認証認可の仕組みを深く理解しなくてもよいのでは？」と思う方もいるかもしれません。しかし、認証認可を正しく学ぶべき理由は複数あります。

### 1. セキュリティ事故の大半は認証認可の不備から起きる

OWASP Top 10（2021）では、「Broken Access Control（アクセス制御の不備）」が 1 位、「Identification and Authentication Failures（認証の不備）」が 7 位にランクインしています。つまり、Web アプリケーションにおけるセキュリティ脅威のトップ 10 のうち、認証認可に直接関わるものが 2 つも入っているのです。

これは、多くの開発者が認証認可の実装を誤っている、あるいは不十分な対策しか行えていないことを意味しています。

### 2. フレームワーク任せでは対処できない場面がある

フレームワークやライブラリは認証認可の基本的な仕組みを提供してくれますが、ビジネスロジックに応じた認可ルールの設計や、マイクロサービス間の認証フロー、外部 IdP（Identity Provider）との連携といった場面では、開発者自身が仕組みを理解したうえで判断する必要があります。

### 3. インシデント発生時に原因を特定できる

認証認可の仕組みを理解していれば、セキュリティインシデントが発生した際に「どのレイヤーで問題が起きたのか」を素早く特定できます。セッションハイジャックなのか、CSRF なのか、権限昇格なのか――原因の切り分けには体系的な知識が不可欠です。

### 4. 設計段階からセキュリティを組み込める

認証認可の知識があれば、後付けのセキュリティ対策ではなく、設計段階からセキュリティを組み込む「Security by Design」を実践できます。手戻りのコストを大幅に削減でき、結果的に開発効率も向上します。

### 5. キャリアの幅が広がる

認証認可は、すべてのプロダクトに共通する横断的な関心事です。この領域の知識を深めることは、シニアエンジニアやアーキテクトとしてのキャリアを築くうえで大きな武器になります。セキュリティレビューや設計レビューの場で、認証認可に関する的確な指摘ができるエンジニアは、チームから高い信頼を得ることができます。

## セキュリティ脅威の全体像

認証認可にまつわるセキュリティ脅威は多岐にわたります。まずは全体像を俯瞰しましょう。

### 認証を狙う脅威

| 脅威 | 概要 |
|:---|:---|
| ブルートフォース攻撃 | パスワードの総当たり試行 |
| クレデンシャルスタッフィング | 漏洩したパスワードリストを用いた他サービスへのログイン試行 |
| フィッシング | 偽サイトでクレデンシャルを詐取 |
| セッションハイジャック | セッション ID の窃取によるなりすまし |
| セッション固定攻撃 | 攻撃者が指定したセッション ID を被害者に使わせる |
| 中間者攻撃（MITM） | 通信の傍受・改ざん |
| リプレイ攻撃 | 正規のリクエストを再送して不正アクセス |

### 認可を狙う脅威

| 脅威 | 概要 |
|:---|:---|
| 水平権限昇格 | 同じ権限レベルの他ユーザーのリソースにアクセス |
| 垂直権限昇格 | より高い権限レベルの機能に不正アクセス |
| CSRF（Cross-Site Request Forgery） | 認証済みユーザーの操作を偽造 |
| IDOR（Insecure Direct Object References） | オブジェクト ID の推測・改ざんによるリソースアクセス |

### アプリケーション全般の脅威

| 脅威 | 概要 |
|:---|:---|
| XSS（Cross-Site Scripting） | スクリプト注入によるトークン・セッション情報の窃取 |
| SQL インジェクション | DB クエリの改ざんによる認証バイパス |
| オープンリダイレクト | 認証後のリダイレクト先を攻撃者サイトに差し替え |

これらの脅威は単独で使われるとは限りません。実際の攻撃では、複数の手法が組み合わされます。たとえば、XSS でセッショントークンを窃取し（アプリケーション層の攻撃）、そのトークンを使ってセッションハイジャックを行い（認証への攻撃）、さらに権限昇格を試みる（認可への攻撃）といった多段階の攻撃が行われます。

このように脅威を「認証」「認可」「アプリケーション全般」の 3 層に分類して理解しておくと、どのレイヤーでどの対策が必要かを整理しやすくなります。本書の各章では、それぞれの脅威に対する具体的な防御策を解説します。

### セキュリティの基本原則

脅威に立ち向かうには、次のセキュリティ原則を常に意識することが重要です。

1. **最小権限の原則（Principle of Least Privilege）**: 必要最小限の権限のみを付与します。デフォルトは「拒否」とし、必要に応じて権限を開放します。
2. **多層防御（Defense in Depth）**: 単一の防御に頼らず、ネットワーク層、アプリケーション層、データベース層の各レイヤーで防御策を講じます。
3. **フェイルセキュア（Fail Secure）**: エラーや例外が発生した場合は、安全側に倒します。認証エラー時はアクセスを拒否し、DB 接続断時はキャッシュを許可せずデフォルト拒否とします。
4. **セキュリティバイデフォルト**: 安全な設定をデフォルトにします。Cookie の `HttpOnly`、`Secure`、`SameSite` 属性の有効化、HTTPS の強制などがこれにあたります。
5. **ゼロトラスト**: 「信頼しない、常に検証する」を徹底します。内部ネットワークであっても信頼せず、リクエストごとに認証・認可を実施します。

これらの原則は抽象的に聞こえるかもしれませんが、本書の各章で具体的な実装パターンとして繰り返し登場します。たとえば、セッション管理の章では「フェイルセキュア」の原則が Cookie 属性の設定に直結しますし、RBAC の章では「最小権限の原則」がロール設計の基本方針となります。

## 認証認可パイプライン

Web アプリケーションにおいて、リクエストがどのような流れでセキュリティチェックを受けるかを理解しておくことは重要です。典型的なパイプラインは次のとおりです。

```
HTTP リクエスト受信
    │
    ▼
① TLS 終端 ─── 通信の暗号化、証明書の検証
    │
    ▼
② レート制限 ─── ブルートフォース・DDoS の防止
    │
    ▼
③ CORS チェック ─── Origin ヘッダーの検証
    │
    ▼
④ 認証（AuthN） ─── Cookie / Bearer Token の検証 → ユーザー ID の特定
    │
    ▼
⑤ 認可（AuthZ） ─── RBAC / ABAC に基づくアクセス制御
    │
    ▼
⑥ 入力検証 ─── バリデーション、サニタイズ（XSS / SQLi 防止）
    │
    ▼
⑦ ビジネスロジック ─── 実際の処理の実行
    │
    ▼
⑧ 監査ログ ─── 「誰が何をしたか」の記録、レスポンス生成
```

このパイプラインで注目すべきポイントは、認証と認可がリクエスト処理の中核に位置していることです。TLS やレート制限といったインフラ層の防御を通過した後、最初に行われるアプリケーションレベルの判断が認証であり、次に認可が続きます。

それぞれのステップを簡単に補足します。

- **TLS 終端**: 通信を暗号化し、中間者攻撃を防ぎます。HTTPS を強制することで、クレデンシャルやトークンの盗聴を防止します。
- **レート制限**: 一定時間あたりのリクエスト数を制限し、ブルートフォース攻撃や DDoS 攻撃を緩和します。
- **CORS チェック**: ブラウザからのクロスオリジンリクエストを制御し、意図しないオリジンからの API 呼び出しを防ぎます。
- **認証**: Cookie やトークンを検証し、リクエストの送信者を特定します。失敗時は 401 を返します。
- **認可**: 特定されたユーザーの権限を確認し、リクエストされた操作が許可されているかを判定します。失敗時は 403 を返します。
- **入力検証**: リクエストパラメータのバリデーションとサニタイズを行い、XSS や SQL インジェクションを防ぎます。
- **ビジネスロジック**: すべてのセキュリティチェックを通過したリクエストに対して、実際の処理を実行します。
- **監査ログ**: 誰がいつ何をしたかを記録し、インシデント調査やコンプライアンス対応に備えます。

本書では、このパイプラインの各要素を章ごとに詳しく解説していきます。

## 本書の構成と対象読者

### 対象読者

本書は、次のような方を対象としています。

- **Web アプリケーション開発者**: フレームワークが提供する認証機能を使っているが、その内部の仕組みを理解したい方
- **バックエンドエンジニア**: API の認証認可を適切に設計・実装したい方
- **フロントエンドエンジニア**: トークンの取り扱いやセッション管理の仕組みを知りたい方
- **セキュリティに関心のあるエンジニア**: OWASP Top 10 に対応した実装パターンを学びたい方
- **チームリーダー・アーキテクト**: 認証認可の設計判断（セッション方式 vs トークン方式、IdP の選択等）に必要な知見を得たい方

前提知識としては、何らかのプログラミング言語の基本的な知識と、HTTP の基礎的な仕組み（リクエスト/レスポンス、ステータスコード等）の理解があれば十分です。

### 各章の概要

本書は 15 章で構成されています。前半で基礎を固め、後半で応用的なトピックを扱います。

| 章 | タイトル | 内容 |
|:---|:---|:---|
| 第 0 章 | はじめに（本章） | 認証と認可の違い、脅威の全体像、本書の構成 |
| 第 1 章 | 認証の基礎 | 認証要素（知識・所有・生体）、MFA、NIST AAL |
| 第 2 章 | パスワードセキュリティ | ハッシュ化、ソルト、bcrypt/Argon2、漏洩チェック |
| 第 3 章 | セッション管理 | Cookie ベース認証、セッション ID の生成と管理 |
| 第 4 章 | CSRF 対策 | SameSite Cookie、CSRF トークン、Origin 検証 |
| 第 5 章 | JWT | 構造、署名検証、アクセストークンとリフレッシュトークン |
| 第 6 章 | OAuth 2.0 | 認可コードフロー、PKCE、スコープ設計 |

| 第 14 章 | ベストプラクティス | セキュリティヘッダー、監査ログ、運用チェックリスト |

各章は独立して読むこともできますが、第 0 章から順に読み進めることで、認証認可の知識を体系的に習得できるように構成しています。

### 本書の読み方

本書は大きく 4 つのパートに分けて読むことができます。

**パート 1: 基礎編（第 0 章 - 第 4 章）**
認証認可の基本概念、パスワードの安全な管理、セッションベースの認証、CSRF 対策を学びます。Web セキュリティの土台となる知識を固めるパートです。

**パート 2: トークン編（第 5 章 - 第 8 章）**
JWT の仕組み、OAuth 2.0 の認可フロー、OpenID Connect による認証、トークンのライフサイクル管理を学びます。モダンな認証認可の中核となる技術群です。

**パート 3: アクセス制御編（第 9 章 - 第 11 章）**
RBAC・ABAC といった認可モデルの設計と、多要素認証の実装を学びます。「誰に何を許可するか」を体系的に設計するための知識です。

**パート 4: 実践編（第 12 章 - 第 14 章）**
ソーシャルログイン、API の認可設計、そして運用で役立つベストプラクティスを学びます。実際のプロダクト開発で直面する課題に対応するパートです。

すでに認証認可の基礎知識がある方は、必要なパートから読み始めていただいても問題ありません。
