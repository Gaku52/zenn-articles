# マルチファイル開発とエージェント活用

Claude Codeは単なるAIアシスタントではありません。複数のエージェントを並列実行し、大規模なコードベースを効率的に操作できる「マルチエージェントシステム」です。この章では、Claude Codeのエージェントアーキテクチャを理解し、数十〜数百ファイルの変更を伴う大規模開発を効率化する手法を学びます。

## Claude Codeのエージェントアーキテクチャ

Claude Codeは階層的なエージェント構造を持っています。

### メインエージェント

ユーザーと直接対話する、セッションの中心となるエージェントです。すべてのツール（Read, Write, Edit, Bash, Grep, Glob, Task等）を使用でき、会話の文脈を保持します。

メインエージェントの役割は次のとおりです。

- ユーザーの要求を理解し、タスクを分解する
- 必要に応じてサブエージェント（Task）を起動する
- サブエージェントから返された結果を統合し、最終的な回答を生成する
- ファイルの読み書きや編集を実行する

### サブエージェント（Task）

メインエージェントが`TaskCreate`ツールで起動する子プロセスです。各サブエージェントは独立したコンテキストを持ち、並列実行が可能です。

サブエージェントの特徴は次のとおりです。

- **独立したコンテキスト**: メインエージェントの会話履歴を引き継がない
- **並列実行**: 複数のTaskを同時に起動できる
- **コンテキスト節約**: 調査結果だけをメインに返すため、メイン側のトークン消費を抑制
- **専門化**: 種類ごとに使用できるツールが異なる

## サブエージェントの種類

Claude Codeには4種類のサブエージェントがあり、それぞれ得意分野が異なります。

### 1. Explore（探索エージェント）

コードベースの探索に特化したエージェントです。

**使用可能ツール**: Glob, Grep, Read

**得意な作業**:
- ファイル検索（「どこに認証処理が書かれているか」）
- パターン検索（「useState を使っている全てのコンポーネント」）
- 依存関係の追跡（「このライブラリを使っている箇所」）
- ディレクトリ構造の把握

**使用例**:

```
> 「認証処理がどこに実装されているか調べてください」
→ ExploreエージェントがGrep, Globで検索し、結果を返す
```

Exploreエージェントは読み取り専用なので、誤ってコードを変更する心配がありません。

### 2. general-purpose（汎用エージェント）

すべてのツールを使用できる汎用エージェントです。

**使用可能ツール**: Read, Write, Edit, Bash, Grep, Glob, 等すべて

**得意な作業**:
- ファイルの作成・編集
- テストの実行と修正
- 複雑なリファクタリング
- ビルドの実行

**使用例**:

```
> 「新しいAPIエンドポイントを追加してください」
→ general-purposeエージェントがファイルを作成・編集し、テストを実行
```

最も柔軟性が高いエージェントですが、その分コンテキストを多く消費します。

### 3. Plan（計画エージェント）

設計・計画立案に特化したエージェントです。コードの変更は行いません。

**使用可能ツール**: Read, Grep, Glob（書き込み系ツールは使用不可）

**得意な作業**:
- リファクタリング計画の立案
- アーキテクチャ設計
- 影響範囲の調査
- タスク分解

**使用例**:

```
> 「認証システムをAuth0に移行する計画を立ててください」
→ Planエージェントがコードベースを調査し、移行手順を提案
```

Planエージェントは`/plan`コマンドで起動する「Plan Mode」とも連携します（後述）。

### 4. Bash（コマンド実行エージェント）

コマンド実行に特化したエージェントです。

**使用可能ツール**: Bash

**得意な作業**:
- テストスイートの実行
- ビルドプロセスの監視
- スクリプトの実行
- Git操作

**使用例**:

```
> 「全てのテストを実行して結果を報告してください」
→ Bashエージェントがテストを実行し、成否を返す
```

## 並列エージェント実行

Claude Codeの最大の強みは、複数のサブエージェントを並列実行できることです。

### 並列実行のメリット

1. **時間の短縮**: 10ファイルの調査を1エージェントで行うと10回の対話が必要ですが、10エージェントなら1回で完了します。
2. **コンテキスト節約**: サブエージェントは独立したコンテキストを持つため、メインエージェントのトークン消費を抑制できます。
3. **並行作業**: 異なる種類のタスク（調査、テスト実行、ビルド）を同時に進行できます。

### 並列実行の例

```
> 「apps/配下の10個のコンポーネントを調査してください」

Claude Code:
- Explore Agent 1: components/Header.tsx を調査
- Explore Agent 2: components/Footer.tsx を調査
- Explore Agent 3: components/Sidebar.tsx を調査
...
- Explore Agent 10: components/Modal.tsx を調査

（10エージェントが並列実行）

結果を統合してメインエージェントが報告
```

メインエージェントは10個のサブエージェントの結果だけを受け取るため、全ファイルの内容を自分のコンテキストに保持する必要がありません。

### 並列実行の戦略

並列実行を効果的に使うコツは次のとおりです。

**独立したタスクを並列化する**:
- 「10個のコンポーネントを調査」→ 各コンポーネントは独立しているので並列化に最適
- 「ファイルAを読んでBを編集」→ 順序依存があるので並列化できない

**サブエージェントの種類を使い分ける**:
- 調査だけならExplore（軽量）
- 編集が必要ならgeneral-purpose

**結果の集約を考慮する**:
- 各エージェントの出力形式を統一すると、メインでの集約が容易

## 大規模リファクタリングの戦略

数十〜数百ファイルの変更を伴う大規模リファクタリングでは、「Plan → 承認 → 実行」の3ステップが有効です。

### Plan Mode（計画モード）

`/plan`コマンドで起動する特別なモードです。

```bash
> /plan
```

Plan Modeに入ると、Claude Codeは次のように動作します。

1. **読み取り専用**: ファイルの変更は一切行わない
2. **計画立案**: タスクを分解し、実行手順を提案
3. **影響範囲調査**: 変更が影響するファイルをリストアップ
4. **承認待ち**: ユーザーの承認を得てから実行に移行

Plan Modeの利用例:

```
> /plan
> 「認証システムをFirebase AuthからAuth0に移行してください」

Claude Code（Plan Mode）:
## 移行計画

### 影響範囲
- 変更ファイル: 23ファイル
- 削除ファイル: 3ファイル
- 新規ファイル: 5ファイル

### 手順
1. Auth0設定ファイルを作成
2. 既存のFirebase Auth呼び出しを特定（12箇所）
3. Auth0のSDKに置き換え
4. テストを更新
5. 環境変数を変更

この計画で進めてよろしいですか？
```

ユーザーが承認すると、Plan Modeを抜けて実行に移ります。

### /batch コマンド（並列大量実行）

`/batch`コマンドは、大規模な変更を5〜30個のユニットに分割し、並列実行する機能です。

```bash
> /batch
```

`/batch`の仕組み:

1. **タスク分割**: 「100ファイルの変更」を「10ユニット × 10ファイル」に分割
2. **git worktree**: 各ユニットを独立したworktreeで実行（コンフリクト防止）
3. **並列実行**: 10ユニットを並列に処理
4. **統合**: 全ユニットが完了したら結果をマージ

`/batch`の利用例:

```
> /batch
> 「全てのコンポーネントでReact 18のAPIに移行してください」

Claude Code:
## Batch実行プラン
- 対象ファイル: 120ファイル
- ユニット数: 12（各10ファイル）
- 推定時間: 5分

実行しますか？ (y/n)

> y

Unit 1/12: components/auth/* ✓
Unit 2/12: components/dashboard/* ✓
Unit 3/12: components/settings/* ✓
...
Unit 12/12: components/utils/* ✓

全ユニット完了。マージを開始します...
```

各ユニットは独立したworktreeで実行されるため、並列実行中にコンフリクトは発生しません。

### Plan → /batch の組み合わせ

大規模リファクタリングでは、`/plan`で計画を立ててから`/batch`で実行する流れが推奨されます。

```
1. /plan で全体像を把握
2. ユーザーが計画を承認
3. /batch で並列実行
4. 結果をレビュー
```

## `--add-dir` による複数ディレクトリ管理

モノレポ（複数のプロジェクトを1つのリポジトリで管理する構成）では、`--add-dir`オプションが便利です。

### 基本的な使い方

```bash
claude --add-dir ../apps --add-dir ../lib
```

これにより、複数のディレクトリをClaude Codeのスコープに含めることができます。

### モノレポでの活用例

```
monorepo/
├── apps/
│   ├── web/        # Next.jsアプリ
│   ├── api/        # Express API
│   └── admin/      # 管理画面
├── packages/
│   ├── shared/     # 共通ロジック
│   ├── ui/         # UIコンポーネント
│   └── config/     # 共通設定
└── CLAUDE.md       # モノレポ全体の構造説明
```

このモノレポで作業する場合:

```bash
cd monorepo/apps/web
claude --add-dir ../../packages/shared --add-dir ../../packages/ui
```

こうすることで、`apps/web`にいながら`packages/shared`や`packages/ui`のコードも参照・編集できます。

### CLAUDE.mdでの構造説明

複数ディレクトリを扱う場合、`CLAUDE.md`にモノレポ全体の構造を記述しておくと効果的です。

```markdown
# モノレポ構成

このリポジトリは以下の構造を持つモノレポです：

## apps/
- **web**: ユーザー向けNext.jsアプリ
- **api**: Express.jsバックエンド
- **admin**: 管理者向けReactアプリ

## packages/
- **shared**: apps間で共有するビジネスロジック
- **ui**: 共通UIコンポーネント（Tailwind CSS）
- **config**: ESLint/TypeScript設定

## 依存関係
- web → shared, ui
- api → shared
- admin → shared, ui
```

Claude Codeはこの情報を元に、適切なディレクトリ間の依存関係を理解します。

## worktree統合

`-w`（`--worktree`）オプションで、隔離されたセッションを起動できます。

### worktreeとは

Git worktreeは、1つのリポジトリから複数の作業ディレクトリを作成する機能です。通常の`git clone`では1ブランチしかチェックアウトできませんが、worktreeを使えば同時に複数ブランチで作業できます。

### Claude Codeでのworktree利用

```bash
claude -w feature-auth
```

このコマンドを実行すると:

1. `feature-auth`という名前でworktreeが作成される
2. 新しいブランチ`feature-auth`がチェックアウトされる
3. Claude Codeがそのworktreeで起動する

### 並列ブランチ作業の例

```bash
# ターミナル1: 認証機能の開発
claude -w feature-auth

# ターミナル2: 管理画面の開発
claude -w feature-admin

# ターミナル3: メインブランチでレビュー
claude
```

各セッションは独立したworktreeで動作するため、コンフリクトが発生しません。

### worktreeとbatchの組み合わせ

`/batch`コマンドは内部的にworktreeを使用しています。手動で`-w`を使う必要はありませんが、仕組みを理解しておくと便利です。

## テスト→修正ループ

Claude Codeは、テストの実行と修正を自律的に繰り返すことができます。

### 基本的なフロー

```
1. テストを実行
2. 失敗したテストを検出
3. エラーメッセージを解析
4. コードを修正
5. 再度テストを実行
6. 成功するまで繰り返す
```

### 実践例

```
> 「全てのテストを実行し、失敗したら修正してください」

Claude Code:
1. テストを実行中...
   → 3件失敗

2. 失敗したテストを分析中...
   - auth.test.ts: トークン検証エラー
   - user.test.ts: null参照エラー
   - api.test.ts: 非同期処理のタイムアウト

3. 修正を適用中...
   - auth.ts を修正（トークン検証ロジック）
   - user.ts を修正（nullチェック追加）
   - api.ts を修正（awaitの追加）

4. 再テスト中...
   → 全てのテスト合格！
```

このループは、ユーザーが介入しなくても自動で回ります。

### 複雑なケース: 並列テスト修正

大規模なテストスイートでは、サブエージェントを並列実行してテスト修正を高速化できます。

```
> 「100個のテストを実行し、失敗したら修正してください」

Claude Code:
1. 全テストを実行: 15件失敗

2. 15件を3つのgeneral-purposeエージェントに分割
   - Agent 1: auth関連のテスト5件を修正
   - Agent 2: user関連のテスト5件を修正
   - Agent 3: api関連のテスト5件を修正

3. 並列実行...
   → 全エージェント完了

4. 統合してテスト再実行...
   → 全テスト合格！
```

## 実践パターン: モノレポでの開発

最後に、これまでの機能を組み合わせたモノレポ開発の実践パターンを紹介します。

### 構成例

```
monorepo/
├── apps/
│   ├── web/        # Next.js
│   └── api/        # Express
├── packages/
│   └── shared/     # 共通ロジック
└── CLAUDE.md       # 構造説明
```

### CLAUDE.md の例

```markdown
# モノレポ開発ガイド

## 構成
- apps/web: Next.js 14（App Router）
- apps/api: Express + TypeScript
- packages/shared: 共通型定義とユーティリティ

## コマンド
- `pnpm test`: 全テスト実行
- `pnpm build`: 全ビルド
- `pnpm dev:web`: webアプリ起動
- `pnpm dev:api`: APIサーバー起動

## ルール
- packages/sharedの変更時は、apps/web, apps/api両方のテストを実行
- APIの型定義はpackages/sharedに配置
- コンポーネントは apps/web/components/ に配置
```

### 開発フロー

**1. 新機能の追加**

```bash
cd monorepo/apps/web
claude --add-dir ../../packages/shared
```

```
> 「ユーザープロフィール編集機能を追加してください。
   shared/types.tsの型を使ってください。」

Claude Code:
1. shared/types.ts を確認
2. apps/web/components/ProfileEditor.tsx を作成
3. APIクライアントを実装
4. テストを作成
5. テストを実行して確認
```

**2. 大規模リファクタリング**

```
> /plan
> 「shared/types.ts の User型を拡張し、全ての使用箇所を更新してください」

Claude Code（Plan Mode）:
## 影響範囲
- apps/web: 12ファイル
- apps/api: 8ファイル
- packages/shared: 1ファイル

## 手順
1. shared/types.ts に新フィールドを追加
2. apps/webの全コンポーネントを更新
3. apps/apiの全エンドポイントを更新
4. テストを更新

この計画で進めますか？

> /batch で実行してください

Claude Code:
Batchモードで実行中...
（20ファイルを4ユニットに分割して並列実行）
完了！
```

**3. テストとデバッグ**

```
> 「全テストを実行し、失敗したら修正してください」

Claude Code:
1. apps/web のテスト実行
   → 2件失敗（ProfileEditor関連）

2. apps/api のテスト実行
   → 1件失敗（User APIエンドポイント）

3. 並列修正:
   - general-purpose Agent 1: ProfileEditorを修正
   - general-purpose Agent 2: User APIを修正

4. 再テスト
   → 全テスト合格！
```

このように、`--add-dir`, `/plan`, `/batch`, サブエージェント並列実行を組み合わせることで、大規模なモノレポでも効率的に開発できます。

## まとめ

| 機能 | 説明 | 使いどころ |
|------|------|------------|
| **メインエージェント** | ユーザーと対話する中心エージェント | 全体の統括と最終判断 |
| **Exploreエージェント** | コードベース探索専用（読み取り専用） | 「どこに何があるか」の調査 |
| **general-purposeエージェント** | 全ツール使用可能 | ファイル編集、テスト実行 |
| **Planエージェント** | 計画立案専用（読み取り専用） | リファクタリング計画 |
| **Bashエージェント** | コマンド実行専用 | テスト実行、ビルド監視 |
| **並列実行** | 複数サブエージェントを同時起動 | 独立したタスクの高速化 |
| **Plan Mode (`/plan`)** | 読み取り専用で計画立案 | 大規模変更の事前調査 |
| **Batch Mode (`/batch`)** | 5-30ユニットで並列実行 | 数十〜数百ファイルの変更 |
| **`--add-dir`** | 複数ディレクトリをスコープに含める | モノレポ開発 |
| **`-w` (worktree)** | 隔離されたセッション | 並列ブランチ作業 |
| **テスト→修正ループ** | 自律的なデバッグサイクル | テストの自動修正 |
