# プロンプトエンジニアリング

LLM（大規模言語モデル）の性能を最大限に引き出す鍵は、**プロンプトの設計**にあります。モデル自体を変えなくても、プロンプトの書き方ひとつで出力品質は劇的に変わります。本章では、プロンプト設計の基本原則から実務で使える高度なテクニックまでを体系的に解説します。

## この章で学ぶこと

- プロンプト設計の **5つの基本原則**
- **Zero-shot / Few-shot / Chain-of-Thought** の使い分け
- **システムプロンプト** の効果的な設計方法
- **構造化出力（JSON mode）** で安定した出力を得る方法
- **プロンプトテンプレート** による再利用可能な設計

---

## 1. プロンプト設計の基本原則

良いプロンプトを書くためには、次の5つの原則を意識することが大切です。

### 原則 1: 具体的に指示する

曖昧な指示は曖昧な出力を生みます。「何を」「どのように」「どの形式で」出力してほしいかを明確に伝えましょう。

```text
# NG: 曖昧な指示
このコードを改善してください。

# OK: 具体的な指示
以下のPythonコードについて、次の3点を改善してください:
1. 型ヒントを追加する
2. docstring を Google スタイルで記述する
3. エラーハンドリングを追加する

改善前と改善後のコードを対比して示してください。
```

### 原則 2: 役割（ロール）を設定する

LLM に「誰として」回答するかを指定すると、専門性のある出力が得られます。

```text
あなたは10年の経験を持つセキュリティエンジニアです。
OWASP Top 10を常に考慮し、具体的な攻撃ベクトルと対策コードを示してください。
```

### 原則 3: 出力形式を指定する

期待する出力のフォーマットを明示すると、後続処理との連携がスムーズになります。Markdown のテーブル、JSON、箇条書きなど、用途に応じた形式を指定しましょう。

### 原則 4: 制約条件を伝える

「300文字以内」「日本語で」「コードブロックを含めて」など、守ってほしい制約を明記します。制約がないと、モデルは自由に解釈してしまいます。

### 原則 5: 重要な指示は冒頭と末尾に置く

LLM には **primacy effect（冒頭重視）** と **recency effect（末尾重視）** があります。最も重要な指示はプロンプトの冒頭か末尾に配置すると、無視されにくくなります。

## 2. Zero-shot / Few-shot / Chain-of-Thought

プロンプトの「型」には代表的な3つのアプローチがあります。タスクの複雑さに応じて使い分けましょう。

### 2.1 Zero-shot（ゼロショット）

例示を一切与えず、直接タスクを指示する方法です。シンプルなタスクや、モデルが十分に理解している領域で有効です。

```text
以下のレビューの感情をポジティブ/ネガティブ/ニュートラルで分類してください。

レビュー: 「このレストランは雰囲気は良かったけど、料理の味は普通でした。」
感情:
```

**向いているタスク:** 単純な分類、翻訳、要約、一般的な質問応答

### 2.2 Few-shot（フューショット）

入出力の具体例を数個提示してからタスクを依頼する方法です。モデルに「こういうパターンで回答してほしい」という期待を伝えられます。

```text
以下のレビューの感情を分類してください。

レビュー: 「最高の体験でした！また行きたいです。」
感情: ポジティブ

レビュー: 「二度と行きません。サービスが最悪でした。」
感情: ネガティブ

レビュー: 「可もなく不可もなく、普通のお店です。」
感情: ニュートラル

レビュー: 「このレストランは雰囲気は良かったけど、料理の味は普通でした。」
感情:
```

Few-shot では例示の **質** と **多様性** が重要です。以下の点を意識しましょう。

- 各カテゴリからバランスよく例を選ぶ
- エッジケース（混合感情、皮肉など）を含める
- 簡単な例から難しい例の順に並べる
- 3〜5個の例示が最適（それ以上はコスト増に対して精度向上が鈍化します）

### 2.3 Chain-of-Thought（思考の連鎖）

「ステップバイステップで考えてください」と指示することで、モデルに段階的な推論を促す方法です。計算、論理推論、複雑な判断で特に効果を発揮します。

```text
Q: 会社の売上が前年比120%で、前年の売上が5億円だった場合、
   今年の売上増加額はいくらですか？

ステップバイステップで考えてください。
```

モデルの出力例:

```text
順を追って考えます。
1. 前年の売上は5億円です
2. 今年の売上は前年比120%なので、5億 × 1.20 = 6億円です
3. 売上増加額 = 今年の売上 - 前年の売上 = 6億 - 5億 = 1億円
答え: 1億円
```

Chain-of-Thought は、Google の研究（Wei et al., 2022）で算数タスクの正答率が **58% から 95%** に向上したことが報告されています。

### 2.4 どの手法を選ぶべきか

| 判断基準 | 選択すべき手法 |
|---------|-------------|
| 単純なタスク | Zero-shot |
| 出力フォーマットが重要 | Few-shot |
| 推論・計算が必要 | Chain-of-Thought |
| 複雑な判断タスク | Few-shot + CoT |

実務では、まず Zero-shot で試し、品質が不十分なら Few-shot や CoT を追加するという段階的アプローチがおすすめです。

## 3. システムプロンプトの設計

システムプロンプトは、LLM の振る舞いを会話全体にわたって制御するための指示です。API 経由で `system` ロールとして設定します。

### 3.1 効果的なシステムプロンプトの構成

良いシステムプロンプトは、**ロール + 行動原則 + 制約事項 + 出力スタイル** の4要素を含みます。

```text
あなたはPython/FastAPIの専門家です。

## 行動原則
- PEP 8 準拠のコードを書く
- 型ヒントを必ず付与する
- エラーハンドリングを必ず含める

## 制約事項
- 推測でコードを書かず、不明点は質問する
- セキュリティ上の懸念があれば必ず警告する

## 出力スタイル
- Markdown 形式で回答する
- コードブロックには必ず言語名を指定する
```

ポイントは、「プログラマーです」のような曖昧なロールではなく「Python/FastAPIの専門家です」と具体的に指定することです。長さは **200〜500トークン** 程度が最適で、長すぎると指示の優先順位が曖昧になります。

### 3.2 XMLタグによる構造化（Claude で特に効果的）

Claude では XML タグを使ってプロンプトの各セクションを明示的に区切ると、指示の理解精度が向上します。

```text
<task>
あなたは技術文書のレビュアーです。
以下の文書を評価し、改善提案を行ってください。
</task>

<evaluation_criteria>
1. 正確性: 技術的な誤りがないか
2. 明確性: 初学者にも理解できるか
3. 完全性: 重要な情報が欠けていないか
</evaluation_criteria>

<document>
（レビュー対象のテキスト）
</document>

<output_format>
各基準について5段階評価とフィードバックを表形式で出力してください。
</output_format>
```

## 4. 構造化出力（JSON mode）

LLM の出力をプログラムで処理するには、JSON などの構造化フォーマットで出力させることが重要です。

### 4.1 JSON 出力を得るための基本パターン

```text
以下の求人情報から構造化データを抽出してください。
必ず以下の JSON 形式で出力してください。他のテキストは出力しないでください。

{
  "company": "会社名",
  "position": "職種",
  "salary_range": {"min": 数値, "max": 数値},
  "skills": ["必須スキル1", "必須スキル2"],
  "remote": true/false
}

求人情報:
「株式会社テックは、フルリモートのシニアバックエンドエンジニアを募集。
Python/Go経験3年以上、年収700-1000万円。」
```

### 4.2 安定した JSON 出力を得るコツ

1. **スキーマを明示する** -- 期待する JSON の構造を例として示します
2. **「他のテキストは出力しないでください」と指示する** -- 説明文の混入を防ぎます
3. **temperature を 0 に設定する** -- 構造が壊れるリスクを最小化します
4. **Pydantic などでバリデーションする** -- 出力を受け取った後に型チェックします

### 4.3 Pydantic と組み合わせた型安全な実装

Python で JSON 出力を扱う場合、Pydantic でバリデーションと型変換を自動化できます。

```python
from pydantic import BaseModel, Field
from typing import List

class JobPosting(BaseModel):
    company: str = Field(description="会社名")
    position: str = Field(description="職種")
    salary_min: int = Field(description="最低年収（万円）")
    salary_max: int = Field(description="最高年収（万円）")
    skills: List[str] = Field(description="必須スキル")
    remote: bool = Field(description="リモートワーク可否")

# LLM の出力を安全にパース
job = JobPosting.model_validate_json(llm_output)
```

### 4.4 APIレベルの JSON mode

主要な LLM API は JSON 出力を保証するモードを提供しています。

| API | 設定方法 | 備考 |
|-----|---------|------|
| OpenAI | `response_format={"type": "json_object"}` | プロンプトに「JSON」の記述が必要 |
| Anthropic | Tool use で JSON スキーマを定義 | スキーマに沿った出力を保証 |
| Google Gemini | `response_mime_type="application/json"` | JSON スキーマの指定も可能 |

API レベルの JSON mode を使うと、プロンプトだけに頼るよりも確実に構造化出力が得られます。

## 5. プロンプトテンプレート

同じパターンのプロンプトを繰り返し使う場合、テンプレート化することで再利用性と保守性が向上します。

### 5.1 テンプレートの基本

変数部分をプレースホルダーにして、実行時に値を埋め込みます。

```python
from string import Template

summary_template = Template("""
以下の文書を${max_words}字以内で要約してください。

要約の条件:
- 主要な論点を全て含める
- 専門用語は平易な言葉に置き換える
- 数値データは正確に引用する

<document>
${document}
</document>
""")

# 使用時に変数を埋め込む
prompt = summary_template.substitute(
    document="人工知能は現代社会において...",
    max_words="200"
)
```

### 5.2 テンプレート運用のベストプラクティス

プロダクション環境では、テンプレートをコードから分離し、バージョン管理することが重要です。

1. **Git で管理する** -- プロンプトも「コード」として扱いましょう
2. **セマンティックバージョニング** -- Major: 出力形式の変更、Minor: 品質改善、Patch: 誤字修正
3. **テストケースを用意する** -- 期待する出力が得られるか自動テストします
4. **評価スコアを記録する** -- 変更前後のスコア比較で回帰を検知します
5. **モデル変更時は再評価する** -- モデルが変わるとプロンプトの効果も変わります

## 6. 実践: プロンプト技法の効果比較

各テクニックの特徴を整理します。プロジェクトの要件に合わせて選択してください。

| 技法 | 実装コスト | 品質向上の目安 | トークンコスト | 最適な場面 |
|------|----------|--------------|-------------|----------|
| Zero-shot | 最低 | 基準 | 最低 | 単純な分類・翻訳 |
| Few-shot | 低 | +10〜20% | 中 | フォーマット統一・分類 |
| CoT | 低 | +20〜40% | 中 | 計算・論理推論 |
| Few-shot + CoT | 中 | +30〜50% | 高 | 複雑な判断タスク |
| XML構造化 | 低 | 安定性向上 | 中 | 長いプロンプトの整理 |
| JSON mode | 低 | 形式の安定化 | 中 | API連携・データ抽出 |
| テンプレート化 | 中 | 再現性向上 | - | プロダクション運用 |

## 7. よくあるアンチパターン

### 曖昧な指示

```text
# NG
「このコードを良くしてください」
→ 何が「良い」のか不明。パフォーマンス？可読性？セキュリティ？
```

### Few-shot 例の偏り

```text
# NG: ポジティブの例だけ
例1: 「すごく良い」 → ポジティブ
例2: 「良い」 → ポジティブ
例3: 「とても良い」 → ポジティブ
→ モデルは全てポジティブと回答する傾向になります
```

### temperature の不適切な設定

| タスク | 推奨 temperature |
|-------|-----------------|
| 分類・抽出・計算 | 0（決定的出力） |
| コード生成 | 0〜0.2 |
| 要約・翻訳 | 0〜0.3 |
| 説明・解説 | 0.3〜0.5 |
| アイデア出し | 0.7〜1.0 |
| 創作・ブレスト | 0.8〜1.0 |

### コンテキストの無駄遣い

不要な背景説明を大量に含めると、本来の指示が埋もれます。必要最小限の情報を簡潔に伝えましょう。

## まとめ

本章で学んだプロンプトエンジニアリングの要点を整理します。

| テーマ | 要点 | 実務での活用ポイント |
|-------|------|-------------------|
| 基本原則 | 具体性・ロール・出力形式・制約・配置 | 全てのプロンプトで意識する |
| Zero-shot | 例示なしの直接指示 | まず最初に試す手法 |
| Few-shot | 入出力例を3〜5個提示 | 分類・フォーマット統一に有効 |
| Chain-of-Thought | 「ステップバイステップで」 | 計算・論理推論で+20〜40%改善 |
| システムプロンプト | 行動原則+制約+出力スタイル | API利用時に必ず設計する |
| 構造化出力 | JSON mode + Pydantic | プログラムとの連携に必須 |
| プロンプトテンプレート | 変数化+バージョン管理 | プロダクション運用の基盤 |
| アンチパターン | 曖昧指示・例の偏り・温度設定 | レビュー時のチェックリストに |
