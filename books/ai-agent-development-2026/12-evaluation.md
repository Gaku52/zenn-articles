## この章で学ぶこと

AIエージェントを開発したら、次に重要になるのが**評価**です。「なんとなく動いている」ではなく、定量的に性能を測定し、継続的に改善していく仕組みが必要です。この章では、LLM評価の基礎からベンチマーク設計、自動評価パイプラインの構築まで、実践的な評価手法を学びます。

## 12.1 なぜエージェント評価は難しいのか

従来のソフトウェアテストでは、入力に対して期待する出力が一意に決まります。しかしAIエージェントの評価には、固有の難しさがあります。

```
従来のソフトウェアテスト:
  入力 → [関数] → 出力（決定的）
  評価: 出力が正しいか？

エージェント評価:
  入力 → [計画] → [ツール1] → [判断] → [ツール2] → ... → 出力
  評価: 最終出力 + 各ステップの妥当性 + 効率 + 安全性
```

エージェント評価が難しい主な理由は以下の3つです。

1. **非決定性**: 同じ入力でも毎回異なる経路をたどる可能性があります
2. **多面的な評価軸**: 「正しい結果」だけでなく「プロセスの質」も重要です
3. **環境依存性**: 外部API・ファイルシステムの状態に結果が左右されます

## 12.2 LLM評価の基礎

### 評価手法の3分類

LLMの評価手法は、大きく3つに分類できます。

| 分類 | 概要 | 信頼性 | コスト |
|------|------|--------|--------|
| **自動ベンチマーク** | 定型のテストセットで機械的に採点 | 中 | 低 |
| **LLM-as-a-Judge** | 別のLLMを評価者として活用 | 高 | 中 |
| **人間評価** | 専門家やユーザーが直接判断 | 最高 | 高 |

実務では、これらを組み合わせて使います。日常的には自動ベンチマークで回し、定期的にLLM-as-a-Judgeで品質を確認し、重要なリリース前には人間評価を行うのが現実的です。

### 主要な自動ベンチマーク

代表的なベンチマークを押さえておきましょう。

```
コーディング系:
  HumanEval   ... 164問のコード生成、pass@k で評価
  SWE-bench   ... GitHubの実Issue解決、テスト通過率で評価
  MBPP        ... 974問のPython基本プログラミング

知識・推論系:
  MMLU        ... 57科目14,042問の4択問題
  GPQA        ... 大学院レベルの科学質問（専門家正答率65%）

エージェント特化:
  GAIA        ... 現実世界の複雑なタスク
  WebArena    ... Webブラウジングタスク
  ToolBench   ... ツール選択と使用の評価
```

ベンチマークのスコアだけを信じるのは危険です。あくまで**特定の能力の近似測定**であり、実際のタスクでの性能を保証するものではありません。自社のユースケースに合った独自の評価セットを作ることが重要です。

### LLM-as-a-Judge

LLM-as-a-Judgeは、LLMそのものを評価者として使う手法です。人間評価に近い柔軟な判定が可能で、スケーラブルに運用できます。

```python
import anthropic, json

class LLMJudge:
    """LLMを評価者として活用するクラス"""

    def __init__(self, model: str = "claude-sonnet-4-20250514"):
        self.client = anthropic.Anthropic()
        self.model = model

    def evaluate(self, task: str, output: str,
                 criteria: list[str]) -> dict:
        """出力を複数の基準で評価します"""
        criteria_text = "\n".join(f"- {c}" for c in criteria)
        response = self.client.messages.create(
            model=self.model,
            max_tokens=1024,
            messages=[{"role": "user", "content": f"""
以下のタスクとその出力を評価してください。

タスク: {task}
出力: {output}

評価基準:
{criteria_text}

各基準について1-5のスコアと理由をJSON形式で出力してください。
"""}]
        )
        return json.loads(response.content[0].text)
```

LLM-as-a-Judgeには**位置バイアス**（最初の選択肢を好む傾向）や**冗長性バイアス**（長い回答を高く評価する傾向）があります。対策として、ペアワイズ比較時にA/Bの順序をランダム化する、複数のLLMで合議制を取るなどの工夫が有効です。

## 12.3 タスク成功率の測定

エージェント評価の最も基本的な指標が**タスク成功率**です。ただし、単純な成功/失敗の二値ではなく、多次元で測定することが重要です。

### 評価の5軸

```
1. 正確性 (Accuracy)    ... タスクを正しく完了したか
2. 効率性 (Efficiency)  ... 少ないステップで完了したか
3. 安全性 (Safety)      ... 危険な操作をしなかったか
4. 堅牢性 (Robustness)  ... エラーから回復できたか
5. コスト (Cost)        ... API費用は許容範囲か
```

### メトリクスの定義と収集

具体的にどのような数値を計測すべきか、レベル別に整理します。

| レベル | 計測する指標 |
|--------|-------------|
| ステップ単位 | ツール選択の正確性、パラメータの正確性 |
| タスク単位 | 成功率、総ステップ数、実行時間、コスト |
| システム単位 | 日次成功率、レイテンシ中央値、安全性インシデント率 |

**注意すべきアンチパターン**: 成功率だけを見て判断するのは危険です。成功率90%でも平均コストが$2.50/タスク、安全違反が5%あれば実用的ではありません。成功率85%でもコスト$0.30、安全違反0%のほうがプロダクションでは優れている場合があります。

## 12.4 ツール利用効率の評価

エージェントの特徴はツールを使えることです。ツールの利用パターンを分析することで、エージェントの賢さを測ることができます。

```python
def calculate_efficiency(total_steps: int,
                         redundant_steps: int,
                         tool_calls: list[dict]) -> dict:
    """ツール利用効率を算出します"""
    efficiency = 1 - (redundant_steps / total_steps) if total_steps > 0 else 0

    total_calls = len(tool_calls)
    error_calls = sum(1 for c in tool_calls if c.get("is_error"))
    tool_error_rate = error_calls / total_calls if total_calls > 0 else 0

    return {
        "efficiency_score": round(efficiency, 3),
        "tool_error_rate": round(tool_error_rate, 3),
    }
```

### 典型的な非効率パターン

| パターン | 説明 | 改善策 |
|----------|------|--------|
| 同じファイルの繰り返し読込 | 一度読んだ情報を忘れて再度読む | コンテキスト管理の改善 |
| 不要なツール呼び出し | 試行錯誤で関係ないツールを呼ぶ | プロンプトの改善 |
| エラーの繰り返し | 同じエラーを何度も繰り返す | エラーハンドリングの強化 |
| 過度な確認行動 | 必要以上に状態を確認する | 信頼度の閾値調整 |

## 12.5 ベンチマーク設計

汎用ベンチマークだけでは不十分です。自社のユースケースに合った**カスタムベンチマーク**を設計しましょう。

### ベンチマーク設計の4ステップ

```
Step 1: タスク収集
  本番環境で実際に発生するタスクをサンプリング（最低50件）

Step 2: 難易度分類
  Easy / Medium / Hard の3段階に分類

Step 3: 正解定義
  各タスクに対する「正解」を定義（検証関数を含む）

Step 4: 自動検証
  テスト通過、出力パターンマッチ、LLM-as-Judgeなどを設計
```

### テストケースの構造例

```python
test_case = {
    "id": "TC-001",
    "name": "ユーザー登録APIのバグ修正",
    "category": "bug_fix",
    "difficulty": "medium",
    "input": "ユーザー登録時にメールアドレスの重複チェックが...",
    "expected": {
        "type": "test_pass",
        "test_command": "pytest tests/test_user.py",
    },
    "metadata": {
        "estimated_steps": 5,
        "max_cost_usd": 0.50,
        "timeout_seconds": 300,
    },
}
```

### ベンチマーク汚染への対策

公開ベンチマークのデータがLLMの学習データに含まれている（データ汚染）場合、スコアが実力を反映しません。対策として以下を心がけましょう。

- **独自テストケースを含める**: 公開データだけに依存しない
- **定期的にテストケースを更新する**: 時間経過で汚染される可能性がある
- **本番データからサンプリングする**: 最もリアルな評価になる

## 12.6 A/Bテストの実践

エージェントのバージョン更新やプロンプト変更の効果を検証するには、A/Bテストが有効です。

### A/Bテストの進め方

```
1. 仮説を立てる
   例:「ツール選択ガイドラインの追加で効率が20%向上する」

2. テストケースを用意する（最低50件）

3. 両方のバージョンで同じテストを実行する
   順序のランダム化、環境の統一を徹底

4. 結果を統計的に検定する
   カイ二乗検定やBootstrap法で p < 0.05 を確認
```

### 測定すべき指標

```python
ab_test_metrics = {
    "primary":    ["task_success_rate"],         # 主要指標
    "secondary":  ["avg_execution_time",         # 副次指標
                    "avg_cost_per_task",
                    "avg_steps", "error_rate"],
    "guardrails": ["safety_violation_rate",      # 悪化禁止指標
                    "p99_latency"],
}
```

A/Bテストの結果を見るときは、p値だけでなく**効果量**も確認しましょう。また、成功率が上がってもコストが倍増していないか、全体では差がなくても特定カテゴリで大きな差がないかをチェックすることが大切です。

## 12.7 自動評価パイプラインの構築

評価を継続的に行うには、CI/CDパイプラインへの組み込みが不可欠です。

### 階層的な評価戦略

すべてのテストを毎回実行するとコストが膨大になります。頻度に応じて階層化しましょう。

| Tier | 頻度 | ケース数 | コスト | 目的 |
|------|------|---------|--------|------|
| 1 | 毎コミット | 10件 | $1-2 | 致命的リグレッション検出 |
| 2 | 毎日 | 100件 | $10-30 | パフォーマンス監視 |
| 3 | 毎週 | 全件 | $50-200 | 包括的品質評価 |

### パイプラインの構成例

GitHub Actionsを使った自動評価パイプラインの骨格です。

```yaml
# .github/workflows/agent-eval.yml
name: Agent Evaluation
on:
  push:
    branches: [main]
  schedule:
    - cron: '0 3 * * *'   # 毎日AM3時
    - cron: '0 6 * * 0'   # 毎週日曜AM6時

jobs:
  smoke-test:
    if: github.event_name == 'push'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: python eval/run_eval.py --tier smoke
      - run: python eval/check_thresholds.py --min-success-rate 0.85

  daily-eval:
    if: github.event.schedule == '0 3 * * *'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: python eval/run_eval.py --tier standard
      - run: python eval/upload_metrics.py
```

### 閾値ベースのアラート

評価結果が基準を下回った場合に自動でアラートを出す仕組みも設定しておきましょう。

| 指標 | 閾値 | 重要度 |
|------|------|--------|
| タスク成功率 | 85%未満 | critical |
| タスクあたりコスト | $1.00超過 | warning |
| ツールエラー率 | 10%超過 | warning |
| P99レイテンシ | 120秒超過 | warning |
| 安全性違反 | 1件以上 | critical |

## 12.8 評価のアンチパターン

よくある失敗パターンを知っておくことで、評価の罠を避けられます。

**1. 成功率のみで判断する** -- 成功率90%でもコストが高すぎたり安全性に問題があれば、プロダクションには投入できません。常に多次元で評価しましょう。

**2. ベンチマークへの過学習** -- 特定のベンチマークに最適化したプロンプトは、汎用性が失われます。独自テストケースも必ず含めましょう。

**3. 評価の非再現性** -- 温度パラメータが高いと毎回結果が変わります。評価時は `temperature=0` に設定し、複数回実行の平均を取りましょう。

**4. 本番データとの乖離** -- 理想的なテストケースだけで評価すると、実際の入力のノイズやエッジケースに対応できません。本番からサンプリングしたデータを含めましょう。

## まとめ

この章で学んだ評価手法を一覧表にまとめます。

| 評価手法 | 自動化 | 精度 | コスト | 適用場面 |
|----------|--------|------|--------|----------|
| 自動ベンチマーク | 完全 | 中 | 低 | CI/CDでのリグレッション検出 |
| LLM-as-a-Judge | 高 | 高 | 中 | 品質の定量評価 |
| 人間評価 | なし | 最高 | 高 | ゴールドスタンダードの作成 |
| A/Bテスト | 中 | 高 | 中 | バージョン比較 |
| ユーザーフィードバック | なし | 高 | 低 | 本番品質の監視 |

| 評価頻度 | 手法 | コスト目安 | 目的 |
|----------|------|-----------|------|
| 毎コミット | スモークテスト | $1-2 | 致命的リグレッション検出 |
| 毎日 | スタンダード評価 | $10-30 | パフォーマンス監視 |
| 毎週 | フル評価 + LLM-as-Judge | $50-200 | 包括的品質確認 |
| モデル更新時 | 全テストスイート | $50-200 | 互換性確認 |

## やってみよう！

以下のステップで、自分のエージェントの評価を始めてみましょう。

1. **評価セットを作る**: 自分のエージェントが扱うタスクを最低20件集め、期待する結果を定義してください。Easy/Medium/Hardに分類しましょう
2. **基本メトリクスを計測する**: タスク成功率、平均ステップ数、平均コストの3つを計測するスクリプトを書いてください
3. **LLM-as-a-Judgeを試す**: 上記のサンプルコードを参考に、エージェントの出力をLLMで採点してみましょう。人間の感覚とスコアがどの程度一致するか確認してください
4. **A/Bテストを実行する**: プロンプトを1箇所変更して、変更前後で成功率に差が出るか検証してみましょう。50件以上のテストケースで比較するのが理想です
5. **CI/CDに組み込む**: スモークテスト相当の10件を、GitHub Actionsなどで毎コミット自動実行する仕組みを作ってみましょう
